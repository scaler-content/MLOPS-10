CI/CD · GitHub Actions · Amazon ECS — Part 2 of 2

A pipeline that works isn't yet a pipeline you can trust

Part 1 built a pipeline that tests and deploys. Nothing stopped a red pull request from being merged, production was the first place an image ever ran, there was no fast way back from a bad release, and failures on main reached no one. This is how all four get closed — plus the one hole that's specific to a model: the pipeline learning to judge whether it's any good.

~35–40 min read Part 2 of 2 — builds directly on Part 1 Release governance · model gates
Why this exists

Four holes in a working pipeline — and a fifth only a model has

Part 1 ended with every pull request tested, and every merge to main that passed going live with no person in between. That shape is right, and a real team would still refuse to trust it with production traffic, for four reasons that have nothing to do with whether the pipeline works.

Nothing is enforced

A red check is advice. The Merge button still works, and anyone with write access can push straight to main.

Production is the first place the image runs

Tests run on a fresh checkout, never on the built image. Part 1 showed a change where every test passed and the image still had no model in it.

There's no quick way back

The circuit breaker rolls back tasks that crash. It can't help with a release that starts fine and simply answers badly.

Nobody is told

Test results reach a pull request's reviewer. A failed run on main, after everyone's moved on, reaches no one.

A machine-learning service has a fifth hole none of those checks even look for. Every one of them examines code. None asks whether the model is any good — before a release or after it. A model trained last month can pass every test today and still be quietly wrong, because the pumps it scores tomorrow aren't the pumps it learned from. This post closes the first four holes completely, and the half of the fifth that fits before a release.

Where this ends up

Every change now takes the same solid path: a pull request, two required checks, a staging copy of the service with a smoke test, a person's approval, and only then production. A second, dashed path — monitoring the live model and retraining it — comes later in the course, and feeds back into the same pull-request path rather than going around it.

The solid row is what this post builds. The dashed row closes the loop later in the course — and plugs into this path rather than going around it.

What you'll be able to do after this
  • Protect main with a ruleset, so every change goes through a pull request and can't merge until named checks pass.
  • Add a model-quality gate that scores a change against main on a fixed holdout set, and blocks a worse model.
  • Split a deploy into staging and production environments, each with its own secret, role and rules.
  • Smoke-test staging from outside, then release the exact same image to production once a reviewer approves.
  • Roll production back to an earlier release in one workflow run — and explain why that's never the whole fix.
  • Open an issue automatically when the pipeline fails on main, so a red run always finds an owner.
  • Explain what none of these checks can see once a model is live, and why that calls for monitoring and retraining.

Assumes everything from Part 1 — workflows, jobs, needs:, permissions:, the ECR repository with immutable tags, and OIDC. Nothing here is new about Docker, ECS or IAM; what's new is how the pieces are arranged.

01 — Picking up where Part 1 ended

The same service, production rebuilt once by hand

The code is the same pump-health service, in a fresh repository, carrying Part 1's tests and pipeline forward and adding three things this session needs.

mlops-cicd-pump-health-2/
pumps.py — stands in for the pumps; makes the readings the model trains on
data/holdout.csv — 5,000 labelled readings no model is ever trained on
infra/up.sh, infra/down.sh — Part 1's AWS commands, collected into two scripts

A pipeline only ever updates a service — it can't create one. So, exactly as in Part 1, production has to exist before any pipeline run. infra/up.sh production does that in one shot: the network, the ECR repository with immutable tags, the OIDC provider, the cluster, the load balancer, the first image, the service, and Part 1's deploy role. Every command checks first whether its resource already exists, so running the script twice changes nothing.

Verifying it landed

One request settles it, exactly as in Part 1: curl $PROD_URL/health should report a git_sha matching git rev-parse HEAD. From this point on, nothing reaches production by hand again — every later change in this post goes out through the pipeline.

02 — Closing the first hole

Rules GitHub enforces

The first hole is the easiest to close, because GitHub closes it for you once you ask. The tool is a ruleset — a list of rules GitHub applies to a branch, for everyone, admins included, unless someone is explicitly named to bypass it. It runs on the server, so no setting on anyone's laptop can get around it.

What protect main turns on

01

No deleting, no rewriting

Restrict deletions and block force pushes — nobody can delete main or rewrite its history, ever.

02

Pull requests only

Require a pull request before merging. Required approvals stays at 0 for a solo repository; a team sets it to 1 or more, so a second person reads every change.

03

Named checks must pass

Require status checks to pass, naming test — the job's ID in pipeline.yml. The Merge button stays grey until it's green.

Two settings worth a second look

Required approvals is how many people other than the author must approve — a team of one can't use it meaningfully, a team of two already should. Require branches to be up to date before merging is left off here: turned on, a pull request re-runs its checks every time main moves, which is safer and slower. Both are fair choices; what matters is that everyone on the team knows which one is in effect.

Proof it's real, not advisory

With the ruleset active, committing straight to main and pushing is refused at the server, before the commit ever lands:

Direct push, refused
! [remote rejected] main -> main (protected branch hook declined) remote: — Changes must be made through a pull request. remote: — Required status check "test" is expected.

The commit still exists locally, so it gets reset away too (git reset --hard origin/main). From here on, every change — in this post and in a real team — goes through a pull request, and the Merge button stays grey until test is green. The next section gives it a second reason to stay grey.

03 — The hole only a model has

A gate for the model

A required test check stops broken code. It does nothing for a worse model, because the tests never ask how good the model is — only whether it loads, whether it answers, and whether a worn pump scores higher than a healthy one. A model can pass every one of those and still miss most of the pumps that are actually about to fail.

The change that slips through every test

Operations says crews are visiting too many healthy pumps and asks for fewer call-outs. Someone raises the decision threshold in train.py from 0.3 to 0.5, retrains, updates the one test that checks the threshold, and opens a pull request. Every test passes. Nobody has asked what the change actually costs in missed failures.

The fix is a second check that scores the model itself, needing three things: data no model was ever trained on (data/holdout.csv, 5,000 labelled readings), a bar to clear (two floors, set just under today's numbers), and something to compare against (the model already on main). evaluate.py does all three.

Recall at the threshold

The share of pumps that really failed which the service would have flagged — the number that matters most, because a missed failure is a burst main.

Pumps flagged

How many crew visits that costs — the trade-off operations is actually trying to tune.

What the gate says about the threshold change

Raising the threshold doesn't touch the model, so ROC AUC doesn't move at all. But at 0.5 the service flags far fewer pumps — and catches far fewer real failures:

Holdout set, 5,000 readings — main (threshold 0.3) vs. this change (threshold 0.5)
ROC AUC is identical (0.855 vs. 0.855) — only the threshold moved.
Recall at the threshold — main (0.3)27.1%PASS
Recall at the threshold — this change (0.5)11.4%FAIL
Pumps flagged — main (0.3)3.8%
Pumps flagged — this change (0.5)1.3%
model-gate: FAIL

Crews would make about a third of the visits — and miss almost nine failures in ten. The change may still be the right business call, but it's now a decision someone makes on purpose, looking at these numbers, not a side effect of a green test run. A team that genuinely wants this lowers the floor in evaluate.py in the very same pull request, where a reviewer sees exactly what they're trading away.

Once proven, model-gate joins test as a job the deploy step needs — and then joins the ruleset itself as a second required check, right alongside it. Both checks now guard main, one for the code and one for the model. Both still run on a checkout of the repository, though — neither has ever once looked at the built image, or the service actually running. That's the next hole.

04 — Two copies of the truth

Two environments

In Part 1, the last check a change got before real users was a test run on a runner — the image was built and pushed straight to production. A problem that only shows up in the built image, or only once the service is really running on ECS, reached users first. The fix every team uses is a staging environment: a second copy of the service that gets every release first, gets checked from the outside, and only then — the exact same image — reaches production.

Staging gets everything of its own that matters: its own cluster, its own load balancer, its own service, its own IAM role. It deliberately shares the network and the ECR repository with production, because production must run the exact image staging just checked.

What a GitHub environment actually is

GitHub has a place built for exactly this. An environment is a named deployment target in a repository's settings — staging or production — and it holds three kinds of things.

A job that names the environment sees them. Any other job in the same repository does not — so staging's role is simply invisible to a job that never opts in.

Required reviewers makes the job wait until a named person approves it. Deployment branches limits which branches may deploy there at all. Prevent self-review stops the author of a change from being the one who approves its own release — left off for a solo class, a team turns it on.

The repository page lists every deployment to each environment, with its commit and when it went out — a running audit trail with no extra tooling.

What changes outside GitHub

A job opts in with one line, environment: production — and that line changes the OIDC token too. In Part 1 the token's subject ended in ref:refs/heads/main. For a job inside an environment, it ends in environment:production instead. A job in staging can never assume the production role, whatever the workflow file says, because AWS checks the subject GitHub actually signed — and a job in production can't even start until a reviewer approves it.

One role per environment, permissions pulling apart

The trust policies differ only after the last colon. The permissions differ far more — staging can build, production never can.

CapabilityStaging roleProduction role
Trust subject ends inenvironment:stagingenvironment:production
Push images to ECRYes — builds every releaseNo — read-only (DescribeRepositories, DescribeImages)
Register task definitionsYesYes
Update a serviceOnly pump-health-staging in mlops-stagingOnly pump-health in mlops-cluster
Hand the execution role to ECSYes, scoped to that one roleYes, scoped to that one role

That asymmetry is the point. If staging's credentials ever leaked, they couldn't touch production. And production's own job can't slip an unchecked image in either — it's physically unable to push, so it can only ever deploy something that already exists in the registry under a tag staging already vouched for.

05 — Checked from outside, then promoted

Staging first, then production

Everything the new pipeline needs now exists, so here's the check it runs on staging. smoke_test.py talks to a running service over HTTP, the way a real client would — not a checkout, not a mock.

The pipeline's shape: one build, two deploys

One build happens, in staging. Production only ever finds and deploys the image that already passed — by its immutable commit tag.

Why no wait-for-service-stability here

The smoke test does the waiting itself, and gives a far better answer: it fails with the commit it actually saw, where the action's built-in wait could only time out or report a generic rollback.

Why one more wait, at the very end

The smoke test passes the instant the new task answers — but ECS keeps the old task in the load balancer for roughly another minute, still serving some requests. So the last step in both jobs explicitly waits until only the new version answers.

concurrency: production

Allows only one job in that group at a time. Two merges close together queue their production releases rather than ever deploying over each other.

One build, two deploys

ECR ends up holding one image per release, not one per environment — production never rebuilds, so it can never run something staging didn't check.

06 — A fast way back

Rolling back on purpose

Every check so far runs before a release. Some problems only show up after one — a model that starts fine but gives answers crews find wrong, or a change that breaks a client nobody tested against. The circuit breaker can't help, because nothing crashed. A revert through a pull request is the right long-term fix, but it goes through the whole pipeline and a review — several minutes, while production keeps doing damage right now.

What makes a fast way back possible is something the pipeline already guarantees: every release is an image tagged with its commit, in a registry where tags never change, and every one of those images already passed staging on its way out. So going back just means deploying an image that already passed — no build, no tests.

A normal release
  • Build the image for this commit
  • Push it to ECR
  • Deploy to staging, smoke test
  • Wait for a reviewer's approval
  • Deploy the same tag to production
vs.
rollback.yml
  • No build. Find an existing image by the commit it was built from
  • Deploy straight to production
  • Smoke test, same as always
  • Still waits for the same reviewer

Started by hand from the Actions tab, with one typed input — the full commit SHA to go back to:

A rollback is never the whole fix

It runs in production, so it uses the same role and waits for the same approval, and concurrency: production keeps it from racing a real release. But main still holds the change that got rolled back from — so the very next merge releases it again, together with whatever else that merge brings. A rollback buys time. A revert or a fix merged to main is what actually finishes the job.

07 — Closing the last hole

Being told when it breaks

A pull request's checks are seen by its reviewer. A run on main has no reviewer — it starts after a merge, once the author has usually moved on, and if it fails the only sign is a red cross on the Actions tab. GitHub does email whoever started the run, but that's one person, and the mail looks like every other GitHub notification.

A better place for a failure is wherever the team already tracks work — here, a GitHub issue, opened automatically by one more job at the end of the pipeline.

Teams on Slack or Teams use the same shape with a different last step — one that posts to a chat webhook stored as a secret instead. What stays the same is a job that runs only on failure, and tells people exactly where to look.

8.1 — The bug Part 1 couldn't catch, caught this time

Here's the exact change from the end of Part 1 that no unit test could ever see: someone adds **/*.joblib to .dockerignore to keep a large local model file out of the build — and it also excludes model/model.joblib, the one the service actually needs. The tests pass, because they run on the checkout, where the file still exists. The gate passes, for the same reason.

Part 1 — no staging

Reached production

Every check green, the image silently missing its model, tasks crashing in the background while the pipeline reported success. Nobody told until someone happened to check git_sha.

Part 2 — staging first

Stopped at staging

After six minutes, the smoke test gives up waiting and fails loudly, with the exact commit it actually saw. Production is never touched. notify opens an issue with no one watching.

Run python smoke_test.py "http://pump-health-staging-alb-…" "19b9f4d6…" FAIL http://pump-health-staging-alb-… still answers with 53f39dd after 300 s, not 19b9f4d Error: Process completed with exit code 1.

The fix is the usual one: git revert -m 1 on the merge commit, through a pull request whose description reads Closes #<issue> — so merging the fix closes the issue in the same motion. The release path is now complete: every change is reviewed, tested, gated, tried on staging, approved, and checked again — and a failure reaches the team on its own, without anyone having to be watching.

08 — The one thing still unguarded

What no check here can see

Every check built in this post looks at something the team controls. The tests look at the code. The gate looks at the model, against a holdout set that never changes. The smoke test looks at the running image. Not one of them ever looks at the pumps themselves.

A scenario nothing here would catch

The utility opens a new station next month. Its pumps are the same kind, but its vibration sensors are a different make, reporting less than half of what the old ones do — and vibration is one of the readings this model leans on most. At that station, a pump shaking itself apart looks perfectly calm to the model, so the service flags almost none of the pumps actually about to fail.

Nothing in this session would notice. The code hasn't changed, so the tests pass. The holdout set has no readings from the new station, so the gate passes. The service answers every request with status: ok, so the smoke test passes and notify never fires. Averaged across every station, the overall numbers might dip only slightly — while at the new station the model is close to useless. The first real sign would be a burst main.

What closes this — later in the course

Compares the live model's answers against what actually happened, once real outcomes are known — checking each station on its own, because one broken group can hide inside a healthy overall average.

Watch the inputs rather than waiting for outcomes — drift can warn before any failures ever arrive, and bias checks catch a model quietly serving some groups worse than others.

The fix that follows a caught drift — training a new model on the world as it actually is now, rather than the world as it was on the day the current model was trained.

Why the solid row had to come first

A retrained model gets no shortcut. It arrives as an ordinary pull request and passes the exact same tests, the same gate, staging and a person's approval as any other change. A retrain that deployed itself would put an unreviewed model straight into production — the release path built in this post is precisely what makes automatic retraining safe to switch on at all.

09 — Reading failure

What goes wrong

Most of this setup's failures were already shown where they belong — a red model gate, a staging deploy that never took over. A few more come specifically with rulesets and environments, and the first is the most confusing one to meet.

A required check that never reports

The ruleset requires a check literally named test — which is the job's ID in pipeline.yml, unless the job has a name: of its own. Someone decides the check list would read better with a human name, and adds one: name: unit tests under the test job.

The job itself runs and passes — now listed as Pipeline / unit tests. And the pull request is stuck forever.

What actually happened

test shows as Expected — Waiting for status to be reported, and it waits forever, because a check with that exact name no longer exists. Nothing is red, so nothing even looks wrong.

The fix

Change the ruleset in the same breath as the job name — or don't rename the job at all. The same trap catches a workflow given paths-ignore: a pull request touching only docs runs no workflow, so its required checks never report either.

A failure that's nobody's fault

A release fails inside the staging job's Build and push the image step — pip times out downloading a package from PyPI (Read timed out).

What actually happened

Nothing is wrong with the change itself — a transient network hiccup during download. notify opens an issue anyway, because from the pipeline's point of view a failure is a failure.

The fix

Re-run failed jobs on the run. Pinned versions decide what gets installed, never whether the download itself succeeds — a team that sees this often enough caches packages or installs from its own mirror. Read the log before blaming the change, and close the issue with a note saying what it actually was.

Approving an old run

Two merges land close together. Both production jobs wait for approval — and approving the older one after the newer one is already waiting would put production back on an older commit.

What protects against it

concurrency: production makes production jobs take turns, and GitHub's documented rule is that a newer pending job in a group cancels an older one that hasn't started yet.

Still worth doing

Test this against your own org's concurrency rules before relying on it blindly — and read the commit shown on the review screen before pressing approve, every time.

A secret that's not there

An environment's secret exists only for jobs that explicitly name that environment. A job that forgets the environment: line gets back an empty secrets.AWS_ROLE_ARN.

The loud version

With the old repository-level secret deleted (as this setup does in section 4), the AWS step fails outright asking for a role — impossible to miss.

The quiet version

If a stale repository secret is ever left behind instead of deleted, the job could quietly succeed using the wrong role — which is exactly why the old one gets deleted, not just superseded.

10 — Housekeeping

Tearing it all down

Everything goes, in both environments — the load balancers, clusters, services, the OIDC provider, both deploy roles, the network. Each teardown check filters by the names this session used, since a shared AWS account can easily hold other people's resources too.

What's worth leaving behind

The GitHub side costs nothing to keep: the ruleset, the two environments and the workflows stay as a record of exactly how the release path was set up. The shared ecsTaskExecutionRole is left in place too, as in Part 1 — only the personal access token from section 1 needs deleting by hand.

11 — The short version

Key takeaways

Part 1 built a pipeline that tests and deploys. This post made it safe to trust — and the work splits cleanly into before a release and during one.

Before a release, GitHub enforces the rules. A ruleset on main refuses direct pushes and holds every pull request until two named checks pass: test, for the code, and model-gate, which scores the change's model on a fixed holdout set no model ever trains on, compared against the model already on main. That gate alone caught a threshold change every single test passed — one that would have missed almost nine failing pumps in ten.

During a release, the image is built exactly once and meets two environments in strict order. staging builds, pushes and deploys to a copy of the service, then a smoke test checks it from the outside until the new commit genuinely answers. production waits for a reviewer, then deploys that same image by its immutable tag — never rebuilding. Each environment carries its own secret and its own IAM role, and each role trusts only the OIDC tokens of its own environment, so staging can never reach production. The exact model-missing bug Part 1 let straight through stopped cleanly at staging this time.

A rollback is never the whole fix. main still holds whatever got rolled back from, so the very next merge releases it again — a revert or a fix on main is what actually finishes the job.

When a run on main fails, notify opens an issue, so a red run always finds an owner. And what none of it sees is the model after release — every check here looks at code, a fixed holdout, or a running image, while the world the model actually scores keeps moving underneath it. Catching that drift is continuous monitoring; fixing it is continuous training — both arrive later in the course, and both plug into this exact release path rather than going around it. A retrained model will walk in as an ordinary pull request, and clear the same tests, the same gate, the same staging, and the same approval as anything else.
